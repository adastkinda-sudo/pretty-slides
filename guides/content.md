# 内容文稿

> 何时读：阶段 1，和用户一起把主题扩展成 `01-content/content.md` 时。

内容文稿是整个流水线的唯一内容来源。后面的设计会话**只读这份文件**，所以它必须完整：讲什么、为什么、按什么顺序、用什么证据、哪些上屏、哪些口头讲。

## 流程

1. **问清楚**（一次集中问，已知的不问）：
   - 讲给谁听？他们已经知道什么？
   - 讲多久？在什么场合（课堂、组会、大会、路演）？屏幕或投影有多大？
   - 听完之后，观众应该能理解或做到什么？（一句话目标）
   - 有哪些必须讲的内容、已有的材料（论文、笔记、数据）？材料放进 `01-content/sources/`。
   - 主题是人物、品牌、作品或风格时：它自己的审美和哲学是什么？要在内容文稿里单独写一节（原则、代表作、做事和讲话的方式，附来源）。设计会话只读文件，这一节是它理解人物的唯一途径。
   - 有没有风格上的偏好或禁忌？（记进 `project.md` 的决策记录）
2. **提出主线**：先给用户一个 5–10 行的大纲：核心论点 + 章节顺序 + 时间分配。让用户先确认方向，再展开。
3. **展开成文**：逐章写出完整的知识内容，包括定义、原理、例子、数据、推导和局限。这一步不追求简洁；精简是设计阶段的事。
4. **核实**：重要的事实、数字和引用都要有来源。有时效性的信息要查当前的来源。区分“事实 / 推断 / 示意”。不确定的写进“待核实”，不要编造。
5. **请用户审阅**：用户可以逐段修改。用户说“可以了”之后，勾选 `project.md` 中的关口 1。

## 写作要求

- **核心论点一句话**能说清楚。说不清楚，说明主题还没想明白，继续和用户聊。
- **叙事有张力**：问题 → 冲突或困惑 → 解释 → 回到问题。不要写成教科书的目录。
- **每章一个要点**，并说明它为什么出现在这个位置（依赖哪个前置知识）。
- **具体**：具体的例子、具体的数字、具体的名字。“极大提升了效率”不如“推理延迟从 800ms 降到 120ms”。
- **为画面准备素材**：在每一章里标出可能成为视觉主体的东西：一个可以画出来的结构、一组对比数据、一张真实的照片、一个反直觉的数字。设计阶段会用到。
- **分配上屏和口述**：每章标出“必须上屏”（公式、关键数据、定义）、“口头讲”和“放进备注”的内容。“必须上屏”每项一行；必须逐字出现在页面上的文字（数字、定义、关键句）用“…”括起来，成稿时 `make.js` 会在整套页面里核对这些文字。不加引号的描述（如“注意力示意图”）不做机器核对；以图片形式上屏的内容（如渲染成图片的公式）也不要加引号。
- **时间预算**：按每分钟 0.7–1.2 页估算总页数，写在简报里。

## 不要

- 不要在内容阶段讨论版式、颜色和字体。
- 不要为了“像 PPT”而把内容写成要点列表。写成完整的段落，设计阶段会提炼。
- 不要编造数据、引用或案例。
