# 渲染自查

> 何时读：每次渲染之后、把结果给用户看之前。

源代码不是视觉证据。每次构建后，都要用 Read 工具打开渲染图（`renders/Sxx.png`），**亲眼看过**再下结论。

## 顺序

1. **看 QA 输出**：`✗` 硬问题全部修掉。`·` 提示是线索，看图后再判断。另外两项：
   - **画面文字核对**（找得到 `02-design/design.md` 时输出）：页面文字和设计文稿的“画面文字”不一致的地方。每一条都要处理：页面漏了就补上；页面上的改动是有意的，就同步回 design.md。
   - **讲解时长估算**：由讲稿字数估算。和 `deck.js` 的 `minutes`（简报里的时长）差得多时，删减或补充讲稿与页面。
2. **退后看**：先看缩略总览（`renders/_contact.png`）。整套是不是同一种语言？强度有没有起伏？有没有哪一页突然变粗糙、变拥挤、变空？
3. **凑近看**：逐页看大图，按下面的硬问题、判断问题、工艺检查过一遍。
4. **拿不准就比较**：做两个版本，用 `node engine/compare.js` 并排看，比单独盯着一个版本判断可靠得多。
5. 修改，然后只重新渲染受影响的页面（`--only`）。
6. **打磨轮次**：普通页一般 1–2 轮；签名画面可以更多轮，并且要做不止一个版本。剩下的问题如果属于设计判断，交给用户，并附上具体建议。
7. **独立审稿**（样张深化和成稿时）：自查做完后，请审稿子代理复查一遍，见下面的“独立审稿”。

## 硬问题（必须修）

| 问题 | 怎么修 |
|---|---|
| 元素意外超出画布 | 移回画布内；有意出血的标 `bleed: true` |
| 文字溢出、被截断、意外换行、出现孤字 | 调整框宽、措辞或换行位置；不要靠缩小字号解决 |
| 单行标签的文本框余量不足（PowerPoint 会意外折行） | `nowrap: true`，或者把框加宽到 1.15 倍以上 |
| 文字与文字、文字与图形意外重叠 | 重新排位置；有意叠压的标 `overlap: true` |
| 对比度不足，或文字压在复杂图像上看不清 | 换成 theme 里更深的颜色；在图像上垫一块纯色 |
| 字体被替换（渲染出来的字形明显不对） | 改用已安装的字体，并更新 theme |
| 数据和图形不一致：数值、比例、坐标轴起点 | 回到数据源修正 |
| `design.md` 要求的元素缺失 | 按设计文稿补上 |
| 讲解页没有图，只有名词和文字 | 按 `data-and-diagrams.md` 的图解配方补一张图；这属于设计层面的改动，同时补写设计文稿 |

## 判断问题（看图判断，明显不好才改）

- **3 秒**：只看 3 秒，能说出这一页的核心信息（design.md 故事串读里的那一句）吗？说不出来，问题通常在主角不突出或文字太多。
- **主角**：最先被看到的是不是这一页的主角？如果不是，放大主角，或者压低抢眼的次要元素。
- **尺度**：是不是所有东西都差不多大？拉开反差。
- **密度**：这一页的满或空，是否和它的任务相符？
- **主题性**：把内容换成另一个主题，这一页是否照样成立？如果是，它还缺少从内容里长出来的东西。
- **强调色**：是否分散在好几处，以至于什么都没被强调？
- **相邻页**：是否和前后页的构图、明暗、密度过于相似（Morph 序列除外）？
- **AI 味**：是否出现了 `anti-ai.md` 里的信号？

拿不准的时候，就不动。少修胜过来回改。

## 工艺检查

成稿最后要专门过一轮，样张阶段也要做。这些细节决定了“还行”和“好看”的差别：

- **对齐**：同一页里的左边缘落在少数几条线上；应该对齐的元素误差不超过 0.03 英寸；跨页的同类元素（标题、页码、导航）位置一致。
- **间距**：同类间距相等；标注和它的对象之间的距离一致。
- **文字**：没有孤字和孤行；中西文之间空格一致；标点没有出现在行首；数字和单位的写法一致；同一个术语在全套写法一致。
- **线条**：线宽成体系（例如结构线 0.5pt、图形线 0.75–1.5pt、重点线更粗），不出现第四种。
- **颜色**：同一含义在全套用同一种颜色；没有“差一点”的近似色。
- **数字**：标注的数值与图形一致，小数位数一致。
- **讲稿**：每页的 `notes` 都是可以照着讲的口语讲稿，和画面一致；括号里只写动作提示（“（单击 1）”“（指着曲线）”），不念出来，也不计入时长。

## 不准动

自查修复**只修执行偏差**，不重新设计：

- 不改 theme 里的颜色、字体和字号层级（这些是用户认可过的设计）。
- 不改页面的构图动作，不增删内容。
- 不改其他页面。

如果问题必须靠这些改动才能解决，就停下来，把它写成给用户的建议：哪一页、什么问题、建议怎么改，最好附上对比图。

## 独立审稿

作者看自己做的页面，容易对问题视而不见。样张深化和成稿在自查之后，请一个**没有参与制作**的审稿人再看一遍。

- **Claude Code**：用 Agent 工具调用 `deck-reviewer` 子代理（定义在 `.claude/agents/deck-reviewer.md`），告诉它 deck 目录和要审的页面 ID（不写就审全部）。它只看渲染图、设计文稿和决策记录，不看代码，不改文件。
- **不能调用子代理的 Agent**：按 `.claude/agents/deck-reviewer.md` 的正文自己再审一遍，并在报告里注明“未经独立审稿”。
- **处理审稿意见**：硬问题全部修掉；判断问题和工艺问题由你决定改不改，不改的说明理由；审稿人标为“超出自查范围”的，按上面“不准动”的规定交给用户。
- 修完重新渲染受影响的页面。不用为同一批修改反复请审稿人复查，除非改动涉及构图。

## 交给用户时

- 给出 pptx 路径和缩略总览（或相关页面的渲染图、对比图）。
- 一句话说明这次做了什么，以及仍然存在的问题。
- 讲解时长估算（和目标时长对比）；是否经过独立审稿，审稿意见中没有采纳的部分和理由。
- 如实区分：“已渲染检查”“QA 启发式检查”“未验证”（例如 Morph 的实际播放、Windows 上的字体）。
